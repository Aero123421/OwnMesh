# v1.2 E2 remote operation routing

E2 connects the public Streamable HTTP MCP surface to the E1 Agent transport and
the policy-gated local `ownmeshd` runtime. Direct filesystem and structured
command operations are first-class. Local coding agents remain optional
downstream tools.

## Production path

```text
ChatGPT / MCP client
  -> user-owned HTTPS /mcp (OAuth bearer + scope)
  -> control-plane Worker
  -> DeviceRoom Durable Object (prepare → durable pending → dispatch)
  -> authenticated Agent WebSocket (ownmesh.device/1.0)
  -> ownmeshd DaemonRuntime (policy gate + side effect)
  -> operation.result → D1 mcp_operations CAS → poll ownmesh_get_operation
```

There is no local fallback when a remote `device_id` is requested. If no
remote-routing-ready Agent is connected, the route fails closed as
`device_offline`.

## Operation contract

Device frames use `ownmesh.operation/1.0`:

- `correlation_id` **equals** `payload.operation_id` (both `op_…`)
- `operation.request` requires `expires_at`, non-empty `capability`,
  non-empty `idempotency_key`, and object `arguments`
- `arguments.action` selects the concrete handler (`fs.list`, `fs.read`,
  `fs.write`, `command.run`, `command.shell`, `cancel`, …)
- Client-supplied `allow` / `approved` / `force` / `skip_approval` /
  principal / policy result / payload hash fields are stripped and are
  **never** authority

MCP tool annotations keep read, write, structured command, and raw shell as
separately authorized actions so ChatGPT app permissions remain meaningful.

## Agent readiness

`ready` advertises:

```json
{
  "capabilities": ["filesystem.read", "filesystem.write", "command.run", "operation.cancel"],
  "operation_contracts": ["ownmesh.operation/1.0"],
  "remote_routing_enabled": true
}
```

DeviceRoom only injects to Agents with `phase=ready` **and**
`remote_routing_enabled=true`. E1-only Agents that advertise `false` stay
fail-closed for remote side effects.

## Exact-once and resume

- Control plane stages pending by `correlation_id` only after durable DO persist
- Agent persists terminal replies before sending `operation.result`
- Replayed correlations return a freshly sequenced cached result and do not
  re-run side effects
- Runtime idempotency keys journal completed allow-path results across process
  restart
- On Agent `ready`, DeviceRoom redelivers durable unfinished pending ops with a
  fresh seq/message_id (Agent cache + runtime journal prevent double side effects)
- Pending TTL/expiry can mark matching MCP ops `OWNMESH_E_OPERATION_EXPIRED`
- Side-effect MCP tools require `idempotency_key`; identical action replays the
  prior row; drifted action fails closed
- Cancel is a separately authorized operation targeting `target_operation_id`

## ChatGPT-centered authorization model

After one-time CLI/TUI setup, ChatGPT is the primary operational and confirmation
UI. OwnMesh:

- treats the authenticated, scoped MCP invocation as the exact requested action
- binds operation identity, tenant/principal (control plane), device, expiry,
  and one-time execution state before dispatch
- does **not** claim ChatGPT supplies a cryptographic confirmation attestation
- does **not** require a second OwnMesh approval UI when device policy allows
- still fail-closes disabled/denied capabilities and maps device policy `ask`
  to `approval_required` for optional local recovery/admin paths

## Bounds

- Agent/DeviceRoom envelopes remain capped at 1,000,000 bytes
- File reads are offset/`max_bytes` windows with `returned_bytes`, `total_bytes`,
  `truncated`, `next_offset`, encoding (`utf-8`|`base64` RFC 4648 padded), and
  SHA-256 of the returned chunk
- Binary Base64 bodies are not re-sliced as text; MCP cursors prefer `off_N`
  byte offsets from the device
- Oversized command/file results are visibly truncated rather than silently dropped
- Post-send DeviceRoom route timeout/throw returns `dispatch_uncertain` and
  leaves the MCP operation **pending** (outbox not marked dispatched) so a
  delayed result can still finalize; identical retries redeliver the bound body
- Agent → control-plane completion path uses a bounded queue + in-flight cap
  (no unbounded completion mpsc under a slow WSS consumer)
