# v1.2 E0 operation contract

E0 froze the cross-language wire contract used by the later v1.2 transport and
routing epochs. E0 alone did not promote a product surface; subsequent E2-E9
implementation and acceptance work now supplies the v1.2.0 remote routes.

## Versioning

- Device envelope protocol: `ownmesh.device/1.0`.
- Operation payload contract: `ownmesh.operation/1.0`.
- A future incompatible payload change requires a new operation-contract major.
- Device-protocol and operation-contract versions are negotiated/evolved
  independently; neither version may be inferred from the other.

## Message types

| Envelope `type` | Direction | Payload purpose |
| --- | --- | --- |
| `operation.request` | Control Plane → Agent | Capability, optional workspace, idempotency key, and object arguments |
| `operation.progress` | Agent → Control Plane | Ordered non-terminal state (`queued`, `pending_approval`, `running`) |
| `operation.event` | Agent → Control Plane | Ordered typed event with object data |
| `operation.result` | Agent → Control Plane | One terminal state and either an object result or a stable error |

## Binding and fail-closed rules

- `correlation_id` is required and must exactly equal `payload.operation_id`.
- `operation.request` requires `expires_at`, a non-empty `capability`, a
  non-empty `idempotency_key`, and object `arguments`.
- `workspace_id` is part of the request identity. The completed E4 path
  propagates it through MCP and enforces the device-local workspace registry and
  policy before filesystem/review/transfer work.
- Progress/event counters and the outer `seq` stay within the JSON safe-integer
  range so Rust and JavaScript cannot disagree about identity or ordering.
- Unknown fields fail closed in the typed operation envelope and payload.
- A completed result requires an object `result` and forbids `error`.
  `failed`, `timed_out`, and `device_offline` require `error` and forbid
  `result`; `cancelled` forbids `result`.
- The completed E3 path binds human approval to the exact validated request
  payload hash, operation identity, owner/tenant, decision, and expiry. Fresh
  passkey admin decisions are consumed exactly once. This remains a later-layer
  property rather than a relaxation of the E0 envelope contract.

## Authorities and fixtures

- JSON Schema: `spec-bundle/schemas/operation-envelope.schema.json`.
- Rust parser/types: `crates/ownmesh-protocol/src/operation.rs`.
- TypeScript parser/types: `packages/ownmesh-schema/src/operation.ts`.
- Golden fixtures: `spec-bundle/examples/fixtures/operation_*_envelope.json`.

Both language suites parse the same four fixtures, validate their bindings,
serialize them, and compare the resulting JSON value with the original. Rust
also validates every fixture against the JSON Schema.

## Surface status

`release/SUPPORTED_SURFACES.json` remains authoritative. In v1.2.0, the later
epochs have promoted authenticated `exec --device`, remote `session open`,
workspace CRUD, streaming approval watch, profile management, transfer, and the
bounded MCP stdio bridge. Remote mutations require explicit idempotency and
never fall back to local execution.

Typed security-admin operations are also implemented without adding a generic
method/parameter passthrough. Their fresh-passkey decision is bound to the exact
recorded action before the device executes it once. The E8 native/public receipt
status and E10 external automation status are evidence disclosures tracked
separately; they do not change this wire contract.
